## 1. Three categories and what the "free" version costs:

**Integers, Python.** A thing in Python is that `a + b` does not and will never overflow. It's because integers just grow as big as they need to. Unlike in our `dt_int.c`, we have to check before every add, subtract, and multiply instead. What Python pays for that is a C `long long` is 8 bytes, while a Python int is a full object on the heap (reference count, type pointer, and digits). So even small values take around 28 bytes. Every `+` also passes through the interpreter as an operation on objects, not a single CPu instruction, and very big numbers take longer the more digits they have. We noticed that in a loop for example that adds millions of numbers. That is why libraries like NumPy use fixed-size machine integers and throws off the "never overflows" promise to get speed and memory. In C, we had to put the checking of input or variables before the operation because signed overflow is an undefined behavvior and an optimizing build is allowed to delete a check written after it. `dt_int_mul` was the longest because of the sign combinations and the `LLONG_MIN * -1` case.

**Arrays, Java.** Java gives bounds checking for free; every `arr[i]` is checked, a bad index throws `ArrayIndexOutOfBoundsException` instead of reading a random memory, and the array keeps its length with its data. What it pays is a length field per array and a comparison on every access. The JIT compiler can drop some of thos checks when it can prove they are safe. But that is the work of the compiler. WEll, it is something we cannot count on. Java arrays also always start at 0. So for indices like -1...1 you would have to do `index - lowerBoun` yourself. This is what exactly what our `dt_array` does with its stored `lower_bound`. In our C version, we wrote all the checks by hand. The part that surprised us is that `index - lower_bound` can itself overflow a `long long` when the lower bound is very negative. That's why `dt_array_get` and `dt_array_set` first rejects `index < lower_bound` then guard the subtraction, then compare the distance with `length`. We also ended up with that said logic written twice: first in `get` and another one in `set`. This works but is the kind of duplication that can drift apart. Probably a single helper would be better and would have been cleaner.


## 2. Hand-written tag check

The obvious thing that C lets us do is skip the checking part `v.as.string` on an int value compiles without a warning. Our `dt_value.c` also only provides checked readers for 3 of the 10 alternatives: int, enum, str. Nothing in the language stops other code from reading `v.as.map` from a value that isnt a map. In Rust, a `match` has to deal with every variant or it will not compile so adding an eleventh tag would force every user to be updated.
What stood out to us more is that the tag check is not the full safety istself; it is only half of the safety. `dt_value_as_enum` checks that the tag is `DT_ENUM` but the constructor `dt_value_enum(47)` will build a value with the right tag and an ordinal that is not a color. We would need  `dt_enum,_is_valid` as well. In Rust, an enum can only be one of its declared variants so that bad value cant be made at all. In our design made, tag says which union member to read, whether the data with it makes sense.
For the question "Is anything C allows worth wanting?", reading the same bytes as another type and controlling the exact memory layout are useful in low-level things like file formats or drivers. For everyday values, we dont think so at all. Skipping the check saves on comparison and the price is `as str 42` handing the printer and integer as if it were an address.


## 3. Dropping the insertion order from `dt_map`

Compared to `dt_map.c`, using an unordered hash map reduces memory overhead by eliminating the secondary ordering array, which costs O(n) extra memory. This secondary array increases memory consumption compared to a standard unordered hash map. Since key-value pairs in an unordered hash map are stored directly in hash buckets, and iteration scans linearly through the table slots. Removing the extra array per map saves memory and simplifies deletions, which no longer need to waste CPU time shifting elements or updating ordering links. A downside of this implementation is that dropping insertion order breaks iteration determinism. Traversing the map yields keys in an arbitrary sequence dictated by hash bucket indexes, which breaks order-dependent serialization. I would personally choose to ship with an unordered hash map mainly because of its ability to lookup in O(1) time. Eliminating the secondary array provides O(1) operations with a smaller memory footprint and cleaner deletions.
